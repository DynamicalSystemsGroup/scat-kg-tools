# RS7-G2: how an LLM tool pauses to ask the person (established practice)

Unit RS7-U2. Fetch date for every URL below: 2026-11-27. Nothing here was tried; it is all
"documented, not tried". Pages were read with WebFetch (a small model summarised each page against
my question, so quotes are brief and paraphrase is mine). GitHub issue and PR metadata (state, dates,
bodies) was read with the public GitHub API (`gh api`). A row marked **summary only** rests on a
search snippet, not a page I read.

Words: coder = the person; tool = our Python package; assistant = the LLM; client = the app that hosts
the assistant (claude.ai, Claude Code, LibreChat, ...). Pattern numbers follow the task.

## 1. The four patterns

| # | Pattern | Who sees the question | Who answers (can the assistant answer for the coder?) | What is recorded | Authority / tell the coder's word from the assistant's guess | Used by (product, URL) | Failure modes in the sources |
|---|---|---|---|---|---|---|---|
| 1 | Assistant asks in its reply (tool result or description tells the assistant to ask; coder answers in chat) | The coder, as ordinary assistant text in the chat | The coder types a chat message. The assistant CAN answer for them: nothing in the protocol separates the two, and the next tool call is written by the assistant | Chat transcript only. Tool result and server logs hold the tool's text and the assistant's next arguments, not who decided | Server cannot tell. A `confirm: true` argument is written by the assistant ("Only set true after the user agreed" was filled in by the model). Nothing in the call proves a person agreed | (a) A shop-inventory MCP server write-up: `confirm` flag, moved to elicitation after the model filled it itself: https://dev.to/sunnatulla_dev/my-mcp-servers-confirm-true-flag-was-written-by-the-model-so-i-moved-the-approval-to-the-user-5dnh (b) iCloud Mail MCP: when the client never answers a form, falls back to a `confirmToken` second call: https://github.com/leolesimple/icloud-mail-mcp/pull/75 (c) Stripe MCP: for "Human confirmation" actions the assistant relays a URL in chat; coder approves out of band (also pattern 3): https://docs.stripe.com/mcp | Assistant skips the preview or fills the flag (dev.to). Preview can differ from the confirmed call (preview `delta: 20`, confirm `delta: 200`). Prompt-injected text in a tool result can steer the assistant (OpenAI MCP guide warns of this: https://developers.openai.com/api/docs/guides/tools-connectors-mcp). Anthropic's directory checklist rejects tool descriptions that tell Claude how to behave ("Describe what the tool does, and don't tell Claude how to behave"): https://claude.com/docs/connectors/building/review-criteria.md |
| 2 | Client-side approval of tool calls (per-tool allow / ask / deny) | The coder, in the client UI: tool name and arguments | The coder clicks. The assistant cannot click, BUT the client can be set to auto-approve ("Always allow", Claude Code `bypassPermissions` and auto mode classifier, VS Code "Allow all", hooks that return allow, SDK `canUseTool` callbacks written by the app developer) | Client side only: permission rules/settings, transcript, hook logs. MCP spec says clients SHOULD log tool usage. The server sees only an ordinary `tools/call` | Server cannot tell whether a person approved or a rule did. MCP spec: tool annotations (destructiveHint etc.) "MUST" be treated as untrusted unless the server is trusted, and are hints, not grants. Claude Code has one server-side lever: `_meta["anthropic/requiresUserInteraction"] = true` forces the prompt every call, even in bypass mode, no "don't ask again" | Claude Code permissions: https://code.claude.com/docs/en/permissions ; its MCP page (requiresUserInteraction): https://code.claude.com/docs/en/mcp ; Claude.ai custom connectors "Always allow" / "Blocked": https://claude.com/docs/connectors/custom/add-unlisted.md ; admin levels Always allow / Needs approval / Blocked: https://support.claude.com/en/articles/11176164-use-connectors-to-extend-claude-s-capabilities ; VS Code Allow Once / Skip: https://code.visualstudio.com/docs/agents/run/approvals ; Cursor asks before MCP tools by default: https://cursor.com/docs/context/mcp ; OpenAI Responses API `mcp_approval_request` / `mcp_approval_response`: https://developers.openai.com/api/docs/guides/tools-connectors-mcp ; OpenAI Agents SDK `needs_approval` / `require_approval`: https://openai.github.io/openai-agents-python/human_in_the_loop/ ; ChatGPT Apps SDK `destructiveHint` ("elicit explicit approval first"): https://developers.openai.com/apps-sdk/reference ; MCP spec "SHOULD always be a human in the loop": https://modelcontextprotocol.io/specification/2025-06-18/server/tools | Prompt fatigue and blanket approvals: VS Code warns "Allow all" and "Always Allow" skip or outlive confirmations; Claude.ai doc says only click Always allow for trusted servers; an "Always allow" setting that did not persist for personal connectors is reported (https://github.com/anthropics/claude-code/issues/56757, summary only). Hints do not decide approval: VS Code says "Tool annotations describe behavior, not permission grants" and `readOnlyHint` skips approval only in a deprecated harness (https://code.visualstudio.com/api/extension-guides/ai/mcp). OpenAI Agents SDK: sticky approvals can carry to another agent after a handoff; approval is not exactly-once. Claude Code SDK: an allow from `canUseTool` still approves a `requiresUserInteraction` tool |
| 3 | Confirm-then-write (preview/dry-run first, second call applies) | The coder sees the preview only if the assistant relays it (or a separate page shows it, as in Stripe) | The second call is made by whoever holds the token. If the assistant holds it, the assistant answers for the coder. If approval happens on a page the server controls (Stripe Dashboard, Terraform human running apply), only the coder can answer | Server state (plan file, approval token, pending request with 24 h expiry in Stripe); Stripe logs MCP calls in Workbench | Tell-apart works only when the approval step is out of the assistant's reach: Stripe issues an approval token after the person clicks Approve in the Dashboard, and "you need to tell the agent to retry"; Terraform saved plan applied by a human. A model-set boolean (`dryRun`, `confirm`) proves nothing | Stripe MCP human confirmation, URL, token, 24 h expiry: https://docs.stripe.com/mcp ; Terraform `plan -out` then `apply <planfile>`: https://developer.hashicorp.com/terraform/cli/commands/plan ; MCP filesystem server `edit_file` with `dryRun` ("Always use dryRun first"; annotations edit_file destructiveHint true): https://github.com/modelcontextprotocol/servers/blob/main/src/filesystem/README.md ; GitHub MCP server: repository deletion "still requires its existing confirmation flow" (only that line seen; page was truncated): https://github.com/github/github-mcp-server ; iCloud Mail MCP `confirmToken` fallback: https://github.com/leolesimple/icloud-mail-mcp/pull/75 ; InfraNodus MCP dry-run plan returned when no answer: https://github.com/infranodus/mcp-server-infranodus/pull/29 | Assistant skips the dry run (filesystem README only advises it). Plan goes stale: Terraform says re-check before applying. Preview and applied call differ if args are re-typed. Stripe: approving does not auto-run, the coder must tell the agent to retry. Terraform plan files hold secrets in cleartext |
| 4 | Protocol elicitation (server asks the client for input mid-call; client shows a form or link) | The coder, in a client dialog labelled with the server name. The assistant does not see the form or the answer in the protocol flow | The coder (accept / decline / cancel). Assistant cannot answer, but the CLIENT can: Claude Code `Elicitation` hook can auto-respond, and several clients auto-decline | Client side: Claude Code `ElicitationResult` hook point; transcript recording not documented (not found). Server gets `{action, content}` | Strongest wire-level signal, but only as good as the client. Server cannot tell a human decline from a client that never showed the form: reported for Claude Code VS Code extension ("indistinguishable from a human explicitly declining"), Claude Desktop (declined ~0.5 s) and Cowork (accepted, never rendered, hangs to 60 s tool timeout). Draft spec forbids secrets in form mode (use URL mode) | MCP spec: https://modelcontextprotocol.io/specification/2025-06-18/client/elicitation and draft https://modelcontextprotocol.io/specification/draft/client/elicitation ; Claude Code (terminal, form + URL, `Elicitation` hook): https://code.claude.com/docs/en/mcp ; VS Code Copilot: https://code.visualstudio.com/api/extension-guides/ai/mcp ; Cursor lists Elicitation: https://cursor.com/docs/context/mcp ; Open WebUI: https://docs.openwebui.com/features/extensibility/mcp ; FastMCP server side (raises error if client lacks support): https://gofastmcp.com/docs/servers/elicitation ; LangGraph `interrupt()`: https://docs.langchain.com/oss/python/langgraph/interrupts ; Google ADK `request_confirmation`: https://adk.dev/tools-custom/confirmation/ ; OpenAI Agents SDK interruptions: https://openai.github.io/openai-agents-python/human_in_the_loop/ | Hangs where capability is declared but not rendered (claude-code#88901, claude-ai-mcp#1085, #1046); auto-decline read as a human no (claude-code#98256, #105334); form delivered on a stream claude.ai connectors never open, so it is dropped and the call times out at 60 s (InfraNodus PR); servers must handle decline, cancel, and client failure (draft spec). Spec: an open dialog may or may not pause tool timers: unclear (apple-native-mcp#25, summary only). LangGraph: node re-runs from the top on resume, side effects before `interrupt()` repeat. ADK: not supported with `DatabaseSessionService` or `VertexAiSessionService` |

## 2. Further established patterns found

| Pattern | Who sees / who answers | What is recorded | Authority / tell-apart | Used by (URL) | Failure modes |
|---|---|---|---|---|---|
| A. Assistant calls a built-in ask tool (`AskUserQuestion`): multiple-choice question rendered by the client | Coder sees a client-drawn question card; coder answers. The assistant writes the question and options, not the answer | Tool result in the transcript (`answers` keyed by question text) | Client-enforced: "always prompts you in every mode, even when an allow rule matches"; denied in `dontAsk`. An SDK app's `canUseTool` callback supplies the answers, so an app could auto-answer | Claude Code: https://code.claude.com/docs/en/permission-modes ; Agent SDK: https://code.claude.com/docs/en/agent-sdk/user-input | Not available in subagents; 1-4 questions, 2-4 options; Claude "can't add your own questions" from the SDK side; auto mode nudges Claude away from asking; VS Code is changing its default free-form handling (https://github.com/microsoft/vscode/pull/336285, open) |
| B. Plan mode: assistant proposes, coder approves the plan before edits | Coder sees the plan; coder picks "Yes ... / No, keep planning". "Claude can't leave plan mode on its own" | Plan file and transcript | Client-enforced gate | https://code.claude.com/docs/en/permission-modes | Approval choice can switch to auto mode ("Yes, and use auto mode"), moving later gates to a classifier |
| C. MCP prompts as coder-initiated slash commands (coder starts the move, no pause needed) | Coder types the command and its arguments; the assistant then receives the prompt text | Transcript shows the command | The coder's word is the command itself; server learns the arguments from `prompts/get` | Claude Code `/mcp__server__prompt`: https://code.claude.com/docs/en/mcp ; Cursor lists Prompts: https://cursor.com/docs/context/mcp | VS Code Copilot sessions do not expose `/mcp.<server>.<prompt>` (https://code.visualstudio.com/api/extension-guides/ai/mcp); Claude Code splits arguments on whitespace, so each is one token; claude.ai and LibreChat prompt UI: not found |
| D. "Input required" tool result (tool returns a typed result asking for input; client collects it and retries the call with the answer) | Coder, through the client; assistant is not in the loop | Retry carries `inputResponses` and opaque `requestState`; server may be stateless | Same trust as elicitation; the retry runs the handler again from the top | Draft MCP spec `InputRequiredResult` (multi round-trip requests): https://modelcontextprotocol.io/specification/draft/server/tools ; Todoist `mcp-core` `request.confirm` returning `asking` (merged 2026-11-27, "not proof the user saw the question", real client not verified): https://github.com/todoist/mcp-core/pull/20 ; LibreChat PR (open, unmerged) that intercepts a server's `confirmationRequired: true` result, shows a modal, re-issues on accept, and hides the envelope from the model: https://github.com/LibreChat-AI/LibreChat/pull/13304 | Client may not render it: claude-ai-mcp#1046 reports a 2026-07-28 `InputRequiredResult` dropped in Cowork, call hangs 180 s. Tool must not write before asking (it re-runs from the top); each question needs its own key |
| E. Out-of-band URL approval (URL-mode elicitation or a vendor approval page) | Coder opens a link; server confirms identity on its own page | Server state | Strong: approval is on the server's own channel; spec requires the server to check the person opening the URL is the same person | Draft spec URL mode: https://modelcontextprotocol.io/specification/draft/client/elicitation ; Stripe: https://docs.stripe.com/mcp | URL mode support is uneven (LibreChat#13267 open; Claude Code VS Code extension#112463 reports "declined by the user" with no dialog) |

## 3. Per-client: what is documented about elicitation and tool approval ("documented, not tried"; fetched 2026-11-27)

### Claude.ai (custom connectors)
- Tool approval, documented: custom-connector tools can be set Always allow or Blocked; "Review tool approval requests carefully" and "Only click Always allow for trusted servers": https://claude.com/docs/connectors/custom/add-unlisted.md . Team/Enterprise owners set Always allow / Needs approval / Blocked per permission category (read-only vs write/delete): https://support.claude.com/en/articles/11176164-use-connectors-to-extend-claude-s-capabilities . Help article on custom connectors tells users to review approval requests and says nothing on elicitation: https://support.claude.com/en/articles/11175166-get-started-with-custom-connectors-using-remote-mcp
- Annotations, documented: every tool "must declare" `readOnlyHint` and `destructiveHint`; "Claude and users read these hints": https://claude.com/docs/connectors/building/mcp.md . The directory checklist says read-only tools "can" run without per-call confirmation and destructive ones "can" require it, depending on user, organisation and conversation settings: https://claude.com/docs/connectors/building/review-criteria.md
- Elicitation: no documentation page found (docs index lists none: https://claude.com/docs/llms.txt ; troubleshooting page silent: https://claude.com/docs/connectors/building/troubleshooting.md ). Claude Code docs say that to claude.ai connectors it declares the bare `elicitation: {}` (form mode only): https://code.claude.com/docs/en/mcp
- Known issues (all open unless noted; state as of 2026-11-27):

### Claude Code
- Elicitation, documented: form and URL dialogs appear automatically in the terminal; `Elicitation` hook can auto-respond (exit 2 declines, no dialog); `ElicitationResult` hook runs after the coder answers; cloud sessions show a card (Submit / Decline); it declares `elicitation: {form:{}, url:{}}` on stdio/http/sse/ws servers in the user's config (v2.1.287+): https://code.claude.com/docs/en/mcp , https://code.claude.com/docs/en/hooks (first ~100k characters only)
- Approval, documented: tiered prompts and modes (`default`, `acceptEdits`, `plan`, `auto`, `dontAsk`, `bypassPermissions`); deny rules block in every mode; MCP rules `mcp__server__tool`; `requiresUserInteraction` forces the prompt: https://code.claude.com/docs/en/permissions , https://code.claude.com/docs/en/permission-modes , https://code.claude.com/docs/en/mcp . `readOnlyHint` and `idempotentHint` are documented as used for parallel runs and retry, not approval.
- MCP prompts as `/mcp__server__prompt`: https://code.claude.com/docs/en/mcp
- Known issues (open): #98256 "capability is declared but requests are auto-declined ('print mode') in interactive VSCode sessions", 2026-09-29: https://github.com/anthropics/claude-code/issues/98256 ; #112463 "VS Code extension 2.1.332: URL elicitation reported as 'declined by the user' with no dialog shown", 2026-11-26: https://github.com/anthropics/claude-code/issues/112463 ; #111077 "MCP client ignores notifications/cancelled for requestId 0, so a pending elicitation dialog cannot be withdrawn", 2026-11-19: https://github.com/anthropics/claude-code/issues/111077 ; #106780 "MCP elicitation prompts not relayed to Remote Control mobile clients", 2026-11-02: https://github.com/anthropics/claude-code/issues/106780 ; #103115 feature: draw the elicitation form while Elicitation hooks run, 2026-10-18: https://github.com/anthropics/claude-code/issues/103115
