## Purpose

Make the approved lifecycle model (WP29) the organising principle of the tools and skills (D-157, D-162). The chief
engineer: "the impliementation is essentially using it as an organizing principle for the tools and skills"; stage
"will alter what tools and skills are exposed, as well as what data is treated as required inputs and what kinds of
data it can produce as output"; "if stage is unknown the MCP server should be capable of returning a result asking for
clarification"; and the server should carry its "instruction manual" (D-157). Words follow `GLOSSARY.md`.

## Goals

- **WP30-G1. The server knows the stage.** A request carries stage as WP29 chose; with no stage or an unknown one, the
  server answers with a result asking for clarification and naming the stages; a stage the user asks for is honoured.
- **WP30-G2. The stage scopes the server.** In a stage the server offers that stage's tools, prompts and skill
  resources, checks its required inputs and allows only its outputs; a call outside the stage gets the clarification
  result WP29 chose, never a silent write.
- **WP30-G3. Transitions.** The server evaluates the predicates it can (from `status`, `check`, the views, `scat.toml`)
  and, when one holds, says which transition is open and asks; a move the user asks for, forward or backward, is made
  when its predicate allows.
- **WP30-G4. The manual, per stage.** For each stage a short guide (purpose, how to recognise it, inputs, outputs,
  tools, the coder's acts, where it can go next or back to, and the docs page); the index with the transitions is sent
  as the server's instructions; each guide is a resource; `scat guide` and `scat guide <stage>` and the API twin give
  the same text. The guides say what `mode` means; the coding guide drafts the account first and finds nodes and edges
  in it one at a time; the analysis guide uses WP28's drawing tools and hands revisits back to the coder.
- **WP30-G5. Skills and prompts by stage.** The skill is sectioned (or split) by stage, and each prompt belongs to a
  stage, as the instance says.
- **WP30-G6. The pages.** The chat and IDE paths and the MCP and CLI references describe stages and how to name one;
  the chat path says field notes may go in a collection on the regular pass ("we use collections on the regular
  inference.coop pass").

## Non-goals

- Changing the model (an amendment to WP29's document, with his approval).
- The wording of the assistant's habits beyond what a stage's guide needs (WP31).
- The IDE path's enforcement: with no server, the stage there is advisory (its guide and `scat guide`).

## Contracts

The MCP interface gains stage on requests, the clarification result, stage-scoped listings, the guide resources and the
instructions; the CLI and API gain `guide`; the machine-interface schema gains their documents. Existing tools keep
their names and fields.

## Definition of good enough

WP30-R1 to R7 met.

## Definition of good

In any stage, the assistant sees only what that stage needs, so the right move is the easy one, and moving between
stages, backward included, is a named, asked-for step.

## Agent's defaults

- *(default)* The server reads WP29's instance data at start; nothing about stages is written twice.
- *(default)* The guide resources are at `scat://guide/<stage>` and `scat://guide/index`; `scat://assistant-rules` stays.
- *(default)* Each guide is at most about 400 words and links to its docs page.
- *(default)* The Claude skill upload stays; the server's guides make it optional.
- *(default)* The on-screen check uses the chief engineer's accounts and keys, with the ACE as coder.
