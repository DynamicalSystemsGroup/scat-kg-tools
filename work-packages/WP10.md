## Purpose

Tighten the path from facilitation to the recorded raw narratives, so the data set is cleaner. Both kinds of
narration stay welcome, but there's less mixing, so the records are easier to interpret afterwards. Each raw scenario
and raw architecture is tagged `past`, `future` or `mixed`. The facilitation guides teach the tag and plan the workshop
so that past and future are taken at separate times.

## Goals

- **WP10-G1. The tag.** A required field on raw scenario and raw architecture pages, working name `timeframe`, with
  the values `past`, `future` and `mixed`. It is defined in the TBox (R-13: one source), with the page contract and one
  rule-catalogue entry. A missing value is an error on a `done` page and a warning before (R-3); any other value is an
  error. `scat stub` writes the field, so nobody types its structure (R-11).
- **WP10-G2. The guidance, in the facilitation guides only.**
  - The planning guide's workshop plan takes past and future at separate times.
  - One list of example phrases, with past and future marked, including non-obvious ones (a counterfactual "what would
    happen if" is future; a habitual "when someone would do x, y happens" is past; anything being done with intention
    but not yet realized is future). It lives in one place, and both facilitation guides link to it.
  - The 2×2 (behavioural or structural, by past or future) is shown once.
  - When to use `mixed`: honestly, when an account blurs the two.
- **WP10-G3. The case study.** The template's raw scenarios and raw architectures carry the tag, chosen from their
  content.
- **WP10-G4. Refresh the candidate.** Re-pin the template, update the walkthrough and reviewer's guide where they
  describe raw pages, and redeploy Pages from `dev`.

## Non-goals

- Coded pages, the four SCAT classes and the three relations: unmarked and unchanged.
- The narrator's normative posture.
- Guidance outside the facilitation guides. The coding guide, the home page and the reference change only where a
  docs test or the generated CLI reference requires it.
- Any analysis of the tag, new CLI commands, the research spikes, WP8-U1.
- Rewriting the facilitation guides. The additions are inserted; existing text changes only where it would contradict
  them.

## Definition of good enough

## Blast radius

- **`scat-kg-tools`:** `ontology/scat.ttl` (the raw page classes and one field only); `contracts/` (the two raw page
  contracts, one catalogue entry, examples); `src/` (only where the field isn't already generated from the TBox, and
  `stub`); `tests/`; `docs/planning.md`, `docs/facilitate-scenarios.md`, `docs/facilitate-architectures.md`; generated
  reference pages if they change; `acceptance/` (walkthrough and reviewer's guide, not `reports/`); the board and
  metrics.
- **`scat-kg-template`:** the raw scenario and raw architecture pages, and the pin files.
- Anything else is out of bounds. A unit that finds it must touch another file stops and asks the ACE.
- **Test edits** that add `timeframe` to existing fixtures, and update assertions that expect the old raw-page output,
  are authorised by the chief engineer directly (log D-058). They are additions only: no check is weakened. Every such
  edit is listed in the unit's report. Briefs quote the authorisation. If a guard still refuses, hold the unit and
  message the ACE.
