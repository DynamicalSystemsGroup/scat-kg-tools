## Purpose

The MCP server offers tools, prompts and the assistant's rules, but nothing that says how they fit the SCAT lifecycle.
The chief engineer (D-157): "the mcp server should have its "instruction manual" built into it. its not a random
collection of tools they exist to support specific lifecycle", with "discovery, and retrieval of markdown files via the
cli ... a simple skills registry organized around the scat project lifecycle", and skills may "direct the user to the
documentation". In both chat runs the assistant did not know what `mode` means, and it listed nodes and edges before any
account was drafted, where in practice "its ofter discovered through the process of coding. same is honestly true of the
nodes". Words follow `GLOSSARY.md`.

## Goals

- **WP29-G0. The stage model, reviewed first.** A written model of the lifecycle the guides rest on: the stages (from the
  flow page's ten steps and the coding loop), the signals that tell which stage a user is in (the vault's state as the
  existing tools report it, what the user says, and when to ask), and every move between stages, forward and backward,
  each with its trigger, who decides, and what to re-check. The flow gives two backward moves (Analyse to Code; `done`
  to `draft`); the model adds those the runs showed (for example Code to Plan when the cap is met, then to the setup
  person) and any others the stages imply. The chief engineer asked for it: "help identify stage transitions since this
  not a linear flow, users may move between stages including "backward" at their discretion". He reviews and approves
  the model at a gate inside WP29 before any guide is written ("ACE drafts, I review").
- **WP29-G1. One guide per stage.** Short markdown guides for the stages of the approved model, and an index that
  carries the model's transitions, each guide saying what the stage is for, how to recognise it, where a user may go
  next or back to, which tools and prompts serve it, the order of work, what
  is the coder's act, and where the docs say more. One source, kept in `scat-kg-tools`.
- **WP29-G2. The server carries it.** The index is sent as the server's instructions when a chat connects; each guide is a
  resource the chat can list and read.
- **WP29-G3. The CLI carries it.** `scat guide` lists the stages; `scat guide <stage>` prints one; the API twin returns
  the text.
- **WP29-G4. What the runs showed is in the guides.** The coding guide puts drafting the account first and finds nodes
  and edges in it, one proposal at a time; the guides say what `mode` means; the analysis guide uses WP28's drawing
  tools and hands revisiting coded data back to the coder.
- **WP29-G5. The pages point to it.** The chat path, the IDE path and the MCP reference say the manual is there and how
  to read it. On the chat path's regular pass, the field notes may go in a collection (the chief engineer: "we use
  collections on the regular inference.coop pass"); leave no trace keeps the temporary chat.

## Non-goals

- Rewriting the assistant's rules or the skill's habits (WP30); the guides link to the rules, they do not restate them.
- New tools beyond reading the guides.
- Replacing the docs site; the guides are short and point to it.

## Contracts

The MCP interface gains the instructions and the guide resources; the CLI and API gain `guide`. The machine-interface
schema gains `guide`'s document. Existing tools and fields do not change.

## Definition of good enough

WP29-R1 to R6 met.

## Definition of good

Any chat or IDE agent connected to SCAT can tell, from what the tools give it, where the coder is in the lifecycle and
what comes next, and says what `mode` means correctly.

## Agent's defaults

- *(default)* The stages are those the approved model names (the flow's ten steps are the starting draft; Discover and
  Decide may fold into one guide).
- *(default)* Recognising a stage uses the existing tools (`status`, `check`, the views, `scat.toml` as reported) and
  asking the user; no new stage-detection tool.
- *(default)* Resources at `scat://guide/<stage>` and `scat://guide/index`; the existing `scat://assistant-rules` stays.
- *(default)* Each guide is at most about 400 words and links to the docs page for its stage.
- *(default)* The skill file stays as it is for Claude's upload; the server's guides make the separate upload optional
  rather than removing it.
