## Purpose

Give the team one common picture of the system before detailed design (`MISSION.md` G16, R-22): what the model, the
views and the control plane are, the modules that make them, each module's interface contract, and who is responsible
for what. Every later package (WP16 to WP20) builds on it. Words follow `GLOSSARY.md`; formal terms only where the
document is precise on purpose.

## Goals

- **WP15-G1. The document.** `docs/architecture.md`, at most 2,500 words plus diagrams, kept on the docs site under
  Reference:
  - **Model, views, control.** The model is the ontology plus a conformant vault; the views (the Obsidian layout, the
    fingerprint view, the edge tables, the layered view, traces) are built from a conformant model and write nothing
    back; the control plane (Obsidian, git and GitHub, the CLI and REPL, the MCP server, IDE agents) acts through the
    tool's operations or through pages the tool then checks.
  - **The three actors and two authorities**, mapped to the modules: where interpretation happens (the coder, in
    Obsidian) and where conformance is decided (the tool: the knowledge graph matches the Markdown, and is
    conformant).
  - **Modules**, each with one purpose, its owner, its interface contract (inputs, outputs, errors, the R-16 data it
    returns), and the goals and requirements that need it. At least: reading a vault into the knowledge graph (the
    public vault loader); the checks; the operations, including recording and removing an edge; mismatch detection
    and fixes (G17, R-23); the shared view generator; the CLI and REPL; the MCP server as a front end; the notebook;
    the template.
  - **Links and edges** (G17): every form a relationship takes, how each pair is held in step, and how incremental
    coding, breadth first or depth first, never leaves a mismatch unseen.
  - **The coding loop and the journey** (J1 to J10) traced across the modules, on the manual path and the chat path.
  - **What is left open** for WP16 to WP18 to decide, each marked.
- **WP15-G2. The review.** Three fresh architecture reviewers (`.claude/agents/architecture-reviewer.md`): two on
  Sonnet (the whole document; the chat path and R-19), one on Opus for the cross-cutting contracts and links and edges
  (G17). Their findings are fixed or answered in a review record, `research/architecture/review.md`.

## Non-goals

- Code, the ontology, page contracts or the layout itself (WP16 onward).
- The chat route, which RS3 chooses; the document leaves a marked slot for it if RS3 hasn't reported.

## Requirements

| ID | Requirement | Checked by |
|---|---|---|
| WP15-R1 | The document covers WP15-G1's six parts, every module has a purpose, an owner, an interface contract and a traced need, and no two modules do one job. | The reviewers; the ACE's read |
| WP15-R2 | Every recommendation of the prior-art readout (WP14) is taken up, or set aside with a reason. | A table in the review record |
| WP15-R3 | The links-and-edges section covers every pair of forms in R-23's list with detection, fix and the incremental case. | The Opus reviewer |
| WP15-R4 | Words follow `GLOSSARY.md`. | A reviewer's read; a grep for the formal terms |
| WP15-R5 | Strict docs build and CI green; `check_metrics.py --accept WP15` passes. | CI; the check's output |

## Definition of good enough

WP15-R1 to R5 met, every reviewer's verdict is "ready for detailed design" or each blocking finding is resolved, and
the ACE approves the document (R-22), logged.
