## Purpose

In the inference.coop run the server held every rule (no `done`, no hand-written row, no page body reached the vault),
but the assistant's words did not: it reported things that were not so, decided what the coder decides, declined for the
wrong reason, and drafted carelessly. The chief engineer asked for the probes "to gather evidence about how it works now
so you can better define the fixes and tests to ensure the behavior is corrected". The probes P1 to P8 and V1 to V3 and
their findings are in `work-packages/WP28-WP31-inputs.md`. Words follow `GLOSSARY.md`.

## Goals

- **WP31-G1. True reports.** The assistant states only what a tool returned, and calls `status` (or the view it is
  describing) before describing the vault.
- **WP31-G2. The coder decides.** It proposes nodes, edges and duplicates and waits for the coder's yes before it
  records; duplicates go through `review` or a merge plan; choices it hands back say what each does and who acts
  (the chief engineer: the "what would happen" column "needs ... filled in").
- **WP31-G3. Declining by role.** When a rule stops it, it says whose act that is (the coder's, or the setup person's for
  a setting), never that a capability is missing, and it does not try the chat's own file tools on the vault.
- **WP31-G4. Careful drafts.** A drafted account follows the template's narrative form, takes facts from the notes only,
  and writes links that resolve; it never tells the coder to hand-write a table row.
- **WP31-G5. The probes as the acceptance test.** P1 to P8 and V1 to V3 become a written test plan with an oracle per
  probe, each probe tagged with the stage it runs in and judged against that stage's tools, inputs and outputs (WP29's
  instance), run on inference.coop and Claude after the change, and compared with the 27 November baseline.

## Non-goals

- Server-side enforcement beyond WP30's stage scoping.
- The stage model (WP29), its implementation and the guides (WP30), and the drawings (WP28); WP31 points to them.
- Re-sectioning the skill by stage (WP30 does); WP31 changes the wording of habits within those sections.
- Choosing or recommending a model for a provider.

## Definition of good enough

WP31-R1 to R5 met, with no probe failing on G1 or G2 on Claude or on inference.coop's default model (the chief
engineer: "both must pass").

## Definition of good

On every provider tried, the assistant tells the truth about the vault, leaves every interpretive call to the coder, and
drafts text the coder can paste as it stands.

## Agent's defaults

- *(default)* The probes run human-paced, one message at a time, on the lab vault, with the chief engineer's sign-ins
  and keys. In these runs the ACE plays the coder and makes the coder's calls (the chief engineer: "where we're using
  chat apps the ACE is roleplaying as me so you can make decisions that in live runs only human coder can make").
- *(default)* The plan adds a probe for each habit the baseline did not cover (for example, options with their effects).
- *(default)* A model that fails a probe on a habit the rules state clearly is recorded, not worked around in the rules.
