## Purpose

Make the tools' output stable for the Obsidian plugin and any later tool, before the first release (log D-060). Every
result is also available as versioned, machine-readable data. Every fix is data a tool can apply, not only a sentence.
The data has a written contract and a versioning rule, so the plugin can build on it without parsing English.

## Goals

- **WP11-G1. The contract.** One JSON Schema file in `contracts/` covers the three result kinds (check, status and
  operation results, refusals included), with an integer `schema_version` starting at 1. A short page in `contracts/`
  states:
  - the versioning rule: adding a field keeps the version, and removing, renaming or changing the meaning of one bumps
    it;
  - that rule ids are stable, and a rule is never renamed, only retired;
  - which fields a consumer may rely on.

  Start from the plugin spike's `prototype/JSON-CONTRACT.md` and `src/contract.ts` on `spike/obsidian-plugin` (read
  them with `git show`). Take what fits; don't inherit what doesn't.
- **WP11-G2. Fixes as data.**
  - Each problem's fix is a list of options. Each option carries:
    - its kind, from the catalogue's fix kinds: exact, options, slot, advisory, manual;
    - for a command, its CLI argument list and its REPL call;
    - for an edit, the file, the field and the value to write, with the *(author)* slot marked;
    - the sentence shown today.
  - The rendered text is generated from this data, so the two can't drift.
- **WP11-G3. Both paths (R-8).** `--json` on every `scat` command prints exactly one JSON document, and the exit code is
  unchanged. Every Python result has an equivalent method that returns the same data. A problem also carries the
  vault-relative file, the line where known, the field, the severity and the rule id. No new runtime dependency (log
  D-056): schema validation runs in the tests only, through a `dev`-group dependency.
- **WP11-G4. Docs.** The API and CLI references show the JSON form once per operation, and link to the contract. The
  coding guide gains at most a sentence.
- **WP11-G5. Refresh the candidate.** Re-pin the template; the docs test, walkthrough and reviewer's guide match; Pages
  redeploys from `dev`.

## Non-goals

- The Obsidian plugin itself, and any change to the spike branches.
- Checking an unsaved editor buffer (`--stdin`), and a public vault loader for analysis (Amendment 4, Agent's
  defaults).
- Changing any rule's trigger, severity or the wording of its text messages, beyond what generating the text from data
  requires. Golden tests may change only where the generated text differs, each change listed.
- WP8-U1.

## Definition of good enough

WP11-R1 to WP11-R7 are met, and the ACE has read the contract page as a plugin developer would: someone who never
opens `src/`.

## Blast radius

- **`scat-kg-tools`:**
  - `src/scat_kg/` (results, checks' fix construction, the CLI);
  - `contracts/` (the schema, the contract page, the catalogue's fix notes where data replaces prose);
  - `tests/`;
  - `docs/reference/` (and at most one sentence in `docs/coding.md`);
  - `pyproject.toml` and `uv.lock` (`dev` group only);
  - `acceptance/` (walkthrough and reviewer's guide, not `reports/`);
  - the board and metrics.
- **`scat-kg-template`:** the pin files only.
- **Test edits.** Golden tests whose text changes only because it is now generated from data are a test edit the
  chief engineer has not authorised for WP11. Keep the text identical where possible. If an existing test must change,
  hold the unit and message the ACE.
